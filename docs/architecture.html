01Overview & Goals

The system manages the full life cycle of a load — from booking through execution on either an owned vehicle or a subcontracted carrier — across multiple operating countries, each with its own currency, cost centre structure, and user base, on one shared platform.

Own fleet + subcontractors

Every load leg is either run by a company vehicle/driver or outsourced. Subcontracted legs carry an independent buy rate and unit of measure, distinct from the customer sell rate.

Built for scale across countries — and customers

One codebase, one database engine, tenant-scoped data (§04) — new countries onboard by configuration, and the same platform can host other, entirely unrelated transport operators with zero cross-visibility between them.

Open by design

A first-class REST API and outbound webhooks let ERPs, customer portals, telematics, and EDI partners integrate without back-door database access.

04Tenancy, Country & Currency Model

Three nested scoping boundaries make this one shared platform rather than one deployment per customer: a Tenant (a single, entirely separate customer of the platform), a Company (one of that tenant's own legal entities, one per operating country), and the Country/Currency context each Company inherits. Only the outer boundary — Tenant — is ever absolute; reporting and roles are free to roll up within it.

4.1Tenant isolation — the SaaS boundary

Rolling this out to other, unrelated transport operators as a SaaS product means one more scoping level above Company: a Tenant is a single signed-up customer of the platform, owning one or more Companies exactly as described below. Two tenants share the same database, application, and infrastructure — and must never be able to see, query, or infer the existence of each other's data.

  • Every table that already carries a CompanyId/CountryId also carries a TenantId, resolved once from the caller's JWT at the very top of the request pipeline — never taken from a request body or query string, so a client can't simply ask for a different tenant's id.
  • Defense in depth, not one filter: an EF Core global query filter scopes every query by Tenant (then Company/Country) at the application layer — the same mechanism already used for country scoping. Underneath that, SQL Server Row-Level Security (RLS) — a built-in database feature, no extra licensing cost — enforces the identical boundary a second time, inside the database itself, keyed off a SESSION_CONTEXT value set once per connection from that same JWT claim. Even a bug that skips the application-layer filter still can't return another tenant's rows, because the database refuses them outright.
  • A "group" role can still roll up reporting across a tenant's own companies — that's unchanged — but no role crosses a tenant boundary, including our own day-to-day platform tooling. The one narrow exception is a heavily restricted, break-glass Platform Support role for our own operations staff, never assignable to a customer's own users, and captured in full by the same audit trail as everything else (§12).
  • Onboarding a new tenant follows the same story as onboarding a new country below: inserting rows — a Tenant, its first Company, an admin user — not provisioning new infrastructure.

4.2Pooled vs. isolated database

Most tenants share one database — the cheapest model to run, and RLS still guarantees one tenant never sees another's rows even though the data physically sits in the same tables. Some customers, particularly larger enterprise accounts, may contractually require full physical separation. Because the scoping key already exists on every row, that's a deployment choice rather than a rebuild: a specific tenant's connection string points at its own isolated database while every other tenant stays pooled, with no application code change either way.

4.3Company, country & currency scoping (within a tenant)

Scoping model

  • Within a Tenant, a Company (legal entity) belongs to a Country, which fixes its default currency, tax regime, and numbering sequence. The Company record is itself master data — legal/trading name, registration number, VAT/tax number, physical & postal address, and banking details — since this is exactly what must appear on every invoice, credit note, and subcontractor load confirmation it issues (see §5.1, §10).
  • Every transactional table (Load, Invoice, Debrief…) carries a TenantId, CompanyId, and CountryId; the same global query filter (§4.1) enforces all three automatically so no query can accidentally cross a company, let alone a tenant.
  • Users are assigned to one or more companies; a "group" role can see roll-up reports across all companies they're granted — always within their own Tenant, never across one (§4.1).

Currency handling

  • Every Client and every Subcontractor record carries a primary CurrencyId, set at onboarding — but a party isn't limited to it: an explicit allow-list (ClientCurrency/SubcontractorCurrency, one row per additional currency) lets a party transact in more than one, e.g. a South African client billed in ZAR for domestic freight and in USD for cross-border export lanes. A RateLine carries its own CurrencyId (defaulting to the party's primary), validated against whichever set applies.
  • Because a client's and a subcontractor's currencies are each set independently, a single load leg can legitimately be sold in one currency and bought in another (e.g. sold to a South African client in ZAR, run by a Mozambican subcontractor in MZN) — and, now, either side can itself be one of several currencies for that same party.
  • No FX conversion in the credit-limit hard stop (§5.4): a client's exposure is tracked per currency, never blended — CreditLimit is per-currency too (the primary's own field, or a ClientCurrency row's for an additional one), so the check that matters most stays exact rather than an approximation of a moving rate.
  • An ExchangeRate table (currency pair, effective date, rate) is refreshed daily from a rate provider via a background job, and can be captured or overridden manually by finance through a dedicated endpoint (§11.2) when a provider rate is missing or disputed.
  • Buy/sell margin on a load leg is calculated in each side's own currency first, then the buy amount is converted to the sell currency using the rate effective on the load date — never re-priced retroactively when rates move.
  • Group-level dashboards convert to a chosen presentation currency at render time; underlying ledgers stay untouched.
  • Granting a client or subcontractor an additional currency — and setting the credit limit that comes with it — is a function-gated action (client.currency.change on the sell side; folded into subcontractor.master.manage on the buy side, since no credit risk is involved there). A party's currencies, once granted, are never revoked through this API — a document already posted in one keeps it, the same "never edit history" rule as everything else in §10.
Implemented: the allow-list, per-currency credit limits, and per-RateLine currency described above are live end-to-end. Verified: a client with a ZAR primary (limit 50,000) and a granted USD allowance (limit 1,000) — an 800 USD sell line was accepted and correctly dropped USD available credit to 200, exactly; a further 300 USD line was rejected for breaching the USD limit while an equivalent ZAR line on the same load posted freely, since the two limits never interact. On the buy side, a subcontractor not granted USD was correctly refused allocation onto a leg already carrying a USD buy rate, while one that was granted it was accepted and had the accrual raised in USD. SupplierInvoice matching refuses to net an accrual against an invoice in a different currency, even for the same subcontractor. Invoice generation confirmed to split cleanly: a client with unbilled sell lines in both ZAR and USD produced one invoice per currency, never a blended document.
Not yet implemented: the ExchangeRate table, its daily refresh job, the manual-override endpoint (§11.2), and the buy→sell currency conversion described above are design only — distinct from the allow-list mechanics confirmed live just above. No ExchangeRate entity, background job, or conversion logic exists yet; Tms.Modules.Rating currently contains only the RateLine entity itself. A load leg sold and bought in different currencies today has no reconciled, currency-converted margin figure — only each side's own-currency amount, independently.
Why scoped-tenant over separate databases: new countries — and new customer tenants — onboard by inserting configuration rows, not by provisioning infrastructure; head-office reporting is a query, not an ETL job; and RLS means the isolation guarantee doesn't depend on remembering to write it correctly every time.

5.1Key entities

Deactivation is enforced, not just labelled: a Deactivated Client can't have a new Load booked against it, a Deactivated Subcontractor can't be allocated to a new leg, and — closed in a follow-up audit, since the OwnFleet path had no equivalent check while the parallel Subcontracted one already did — a Deactivated Vehicle or Driver can no longer be assigned to a leg either, at AddLeg or AllocateLeg. Settling an already-existing relationship (invoicing a client's delivered loads, matching a subcontractor's supplier invoice against its accruals) is deliberately unaffected — deactivation stops new business, not the wind-down of what's already committed. Verified live: assigning a just-deactivated vehicle/driver to a new leg is rejected with 409 at both AddLeg and AllocateLeg; reactivating them makes the same call succeed again. Reactivate is now symmetric with Deactivate for Client and Subcontractor too — both used to be one-way traps with no path back to Active, even though LoadsController's own error messages ("reactivate it before booking a new load") assumed one existed; they now follow the same Deactivate/Reactivate pair every other master-data controller already has. A concurrent-duplicate race on AddCurrency for both — two calls granting the same (Client, Currency) or (Subcontractor, Currency) pair racing past the pre-check — used to surface as a raw 500; it's now a clean 409, verified live for both.

5.4Credit control

Every Client carries a CreditLimit in its fixed billing currency (§04) — a hard ceiling on how much unpaid-plus-unbilled exposure the company will carry for that client at any one time. Exposure has two components: what's already been invoiced but not yet paid, and WIP — the sell value of every load for that client that hasn't reached Invoiced status yet (§5.2).

TermDefinition
AR OutstandingSum of Issued / Part Paid invoice balances for the client, net of any credit notes — the aged breakdown of this figure (Current, 30/60/90/90+ Days) is formalized in §10.3

Available CreditCreditLimit − Total Exposure
  • Hard stop: creating a new load, or increasing an existing load's sell value (e.g. adding a leg), is rejected outright by the API — not merely flagged in the UI — whenever it would push Total Exposure above CreditLimit. The check runs server-side on every channel that can create a load, including the customer portal and EDI integrations (§11), so it can't be bypassed by going around the main screen.
  • Because WIP moves into AR the instant a load is invoiced, and AR shrinks as invoices are paid, Available Credit recovers automatically as the pipeline progresses — nothing needs to be manually reset.
  • A narrow, function-gated override (client.creditlimit.override) lets a credit controller push a specific load through over the limit with a mandatory reason, fully audited; without that function, the stop is absolute.
  • Available Credit is also surfaced directly to the client through the Customer Portal (§13.2), so "why was my load rejected" is self-service rather than a support ticket.
  • Concurrency: the check-and-save is atomic per client — creating a load and adding a commodity line each open a transaction and take an exclusive, transaction-scoped SQL Server application lock (sp_getapplock, keyed on Tenant+Client) before reading exposure, so a second write against the same client blocks until the first commits or rolls back, then reads exposure that already reflects it. Different clients never contend with each other. Verified under genuine concurrency: five simultaneous requests against a client with only enough headroom for two were resolved to exactly two approvals and three rejections, with Available Credit landing at exactly zero, never negative.

5.5Commodities & multi-product loads

A leg isn't always one product at one rate. A fuel tanker delivering 20,000 litres of diesel and 8,000 litres of petrol on the same trip needs both quantities captured separately, and — because the two commodities are very often priced differently — rated separately too. Every leg carries one or more CommodityLines instead of a single price; a general-cargo leg is simply the common case of exactly one.

  • Commodity is company-level master data (its own screen) — diesel, ULP95 petrol, paraffin, or non-fuel product lines like cement or grain — each with a default unit of measure, so "litres" is never hand-typed for a fuel commodity.
  • Each CommodityLine on a leg records what was actually carried — the commodity and the quantity — and carries its own sell RateLine and, where relevant, its own buy RateLine (§08). Two commodities on the same leg can be priced on completely different bases (e.g. diesel per litre, a dry-goods pallet on the same run per pallet).
  • A load/leg's total sell value (used throughout §5.2's status lifecycle and §5.4's credit check) is the sum of every commodity line's sell amount, not a single figure entered once.

5.6Ancillary services (e.g. armed escort)

Some legs need more than moving the commodity — a fuel run through a high-risk corridor might require an armed escort; others might need an abnormal-load permit or fumigation. These are billable to the client like anything else, and where the service is outsourced, they generate exactly the same kind of subcontracted cost as running the leg itself.

  • An AncillaryServiceType is company-level reference data (Armed Escort, Abnormal Permit, Fumigation, …). A leg can carry zero or more AncillaryServiceLines alongside its commodity lines.
  • Each ancillary service line has its own sell RateLine — the client is billed for the escort as its own charge, not folded into the freight rate — and, if the service is outsourced (e.g. to a security company held as a Subcontractor record), its own buy RateLine.
  • An outsourced ancillary service runs through the identical accrual → supplier-invoice-matching pipeline already built for transport subcontracting (§10.2) — the accrual and expense simply reference this line's buy RateLine rather than the transport one, so a single leg can owe two different subcontractors (the carrier and the escort provider) independently, each reconciled against their own invoice.

8.1Margin calculation

Sell Amount and Buy Amount are each computed per line, in their own transaction currency (Rate × Quantity). Margin per line is derived by converting Buy to the Sell currency using the exchange rate effective on the load's execution date, then Margin = SellAmount − BuyAmount(converted); a leg's total margin is the sum across all of its commodity and ancillary service lines. The conversion rate used is stored on the line at debrief/invoicing time so historic margin reporting never drifts when FX rates later change.

Own-fleet legs still carry an internal "buy" cost, computed from a standard cost-per-km/hour table per vehicle class, so margin reporting is consistent whether a leg is run in-house or outsourced.

8.2Subcontractor load confirmation

The moment a leg's ExecutionType is set to Subcontracted and a SubcontractorId is assigned — i.e. as soon as the leg reaches Allocated (§5.2) — the system generates a Load Confirmation: the carrier's written instruction to run the leg, and formal proof of the rate agreed, issued before execution starts.

  • Letterhead pulls straight from the Company master (§5.1) — legal name, address, registration and VAT numbers — and is addressed to the subcontractor.
  • Body shows the load/leg reference, origin and destination, pickup and delivery windows, and every commodity or ancillary service line this subcontractor is responsible for, each with its own agreed RateLineBuy (rate, unit of measure, quantity, and total, in the subcontractor's fixed currency) — so a carrier running a multi-product fuel leg sees the rate for each product separately, and a security provider handling only the escort sees just that line.
  • Issued as a PDF — emailed to the subcontractor and retrievable via the API — with an optional acknowledgement step before dispatch is allowed to proceed, configurable per company. In practice this acknowledgement happens through the Supplier Portal (§13.3), where the confirmation is the first thing a subcontractor contact sees.
  • Issuing the confirmation is also the trigger point for the buy-side accrual (§10.2) — the company's liability to the subcontractor is recognised here, not weeks later when their invoice eventually arrives.

  • Invoices are raised per Client, in that client's fixed currency, aggregating one line per approved commodity or ancillary service line (§5.5, §5.6) — so a multi-product fuel delivery with an escort produces one invoice with a line per product plus a line for the escort, not one blended figure — either on a scheduled run (e.g. daily) or on demand.   • Invoice lifecycle: Draft → Issued → Part Paid / Paid, with Overdue derived from due date. Void/cancel is only permitted while still Draft.
  • A credit note adjusts an issued invoice — rate disputes, short-delivery, damage claims — always linked back to the invoice line(s) it corrects, in the same client currency. Raising one requires the finance.creditnote.approve function, since it reduces recognised revenue.
  • A standalone credit note (not tied to a prior invoice) is supported for goodwill/ad-hoc adjustments, but still requires the same approval function.
  • Issued invoices and credit notes are visible directly to the client through the Customer Portal (§13.2) — no separate export or emailing step required for the client to see their own statement.
  • A sell RateLine can be billed at most once — a unique database constraint, not just the application-layer check — so two concurrent Generate calls racing over the same client's unbilled lines can't both invoice the same line.

10.3Financial calendar & debtors roll-over

Every Company runs its own financial calendar — a FinancialYear divided into FinancialPeriods, each with an explicit opening and closing date — because invoicing, credit notes, and subcontractor expenses all need to post against a period, not just a date, for period-end reporting and reconciliation to mean anything.

  • A financial year need not follow the calendar year (a South African company's tax year, for instance, commonly runs March–February) and is divided into periods — typically 12, sometimes 13 with a stub/adjustment period. Exactly one period per Company is ever Open at a time — enforced by a filtered unique database constraint, not just an application-layer check, so two concurrent requests that both create/close a period can't both open one; every Invoice, Credit Note, and Subcontractor Expense records the period it falls into automatically, resolved from its date rather than hand-picked.
  • Period close is a function-gated action (finance.period.close) and, like every other approval boundary in this design (§09, §10.1, §10.2), is one-directional: once a period is Closed, nothing new can post into it — a correction afterwards is always a new document in the next open period, never a backdated edit.
  • Closing a period and opening the next happen as one operation, so there is never a gap where no period is open and a new invoice would have nowhere to post.
A follow-up audit found Close vulnerable to a double-close race the "one Open period" unique index doesn't cover, since it only guards two different periods becoming Open at once, not the same period being closed twice: two concurrent Close calls for one period both passed the in-memory Status check and each wrote a full, duplicate set of DebtorsAgingSnapshot rows — nothing in that table enforces one row per (Client, Period), so the double-insert went undetected rather than throwing, corrupting the debtors-aging report. Close now atomically claims the period's Status before writing anything else, inside the same transaction as the snapshot writes and the next-period open. Verified live: two concurrent Close calls on the same Open period resolved to exactly one 204 and one clean 409; the closed period's debtors-aging report showed exactly one snapshot row per client, and the next period opened correctly.

Pre-close checklist: closing isn't a single unconditional click. Before confirming, the Finance Clerk sees what's still outstanding for the period about to close — a soft gate, not a hard block, since some of these are genuinely outside the company's control (a subcontractor's invoice hasn't arrived yet is a fact, not an error):

  • None of this changes what closing actually does (§10.3 above) — it's a checklist in front of the same one-directional action, not a new state.

11.1Authentication

  • Interactive users — JWT bearer tokens issued after ASP.NET Core Identity login, short-lived with refresh tokens. This covers internal staff, and — with a fixed ClientId or SubcontractorId claim baked into the token — the Customer and Supplier Portals (§13.1) too.

  • A uniform AuditEntry (Id, EntityType, EntityId, Action, ChangedByUserId?/ApiClientId?, ChangedAtUtc, OldValueJson, NewValueJson, Reason?, CompanyId) is written by an EF Core SaveChanges interceptor — the same code path every module already goes through — so coverage doesn't depend on each module remembering to log itself.

The practical effect: a Client contact hitting any subcontractor-scoped action (AccrualsController.List, SupplierInvoicesController.List, LegsController.SubmitDebrief/AcknowledgeConfirmation) was treated as unrestricted staff and could see every subcontractor's accruals/payables or submit a fabricated POD/claim against any leg — and symmetrically, a Subcontractor contact could see every client's loads/invoices or self-service-book a load for any client. Separately, LoadsController's AddLeg/AllocateLeg/StartLeg/DeliverLeg/Hold/ReleaseHold/Cancel/AddCommodityLine carried no function policy at all — harmless before Portal contacts existed, since class-level [Authorize] only ever needed to mean "authenticated staff," but now reachable by any authenticated portal contact of either type — and ClientsController/SubcontractorsController's List/Get/Currencies actions had no portal check whatsoever, leaking every client's credit limit or every subcontractor's banking details to any portal caller. All closed: the shared check now requires both scoping fields to be null for "unrestricted staff," every List action explicitly Forbids the wrong portal type rather than silently skipping its filter, the eight previously-unguarded Load mutation actions now Forbid any portal caller outright (none of them are part of either portal's documented scope), and the two master-data browsing controllers do the same. Contact provisioning (SubcontractorContactsController/ClientContactsController.Create) and UsersController.AddCompanyRole now also validate that a Role handed to a portal contact grants only the matching portal.* functions and stays within the Company that actually owns their Subcontractor/Client — previously unenforced entirely. Verified live: every cross-type combination (Client contact against every subcontractor-scoped action and vice versa), every previously-unguarded Load mutation, and both master-data controllers now return a clean 403 for a portal caller; assigning a portal contact a non-portal Role (via either contact creation or AddCompanyRole) is rejected with 400; every legitimate own-party action and every internal-staff action verified in the original build still passes unchanged.
A second follow-up audit, scoped specifically to every controller the first one didn't touch, found seven more actions reachable by any portal caller purely because they carried no function policy at all — the exact same root cause as the Load mutation actions above, just in different controllers: DebriefsController.List/Get (a second, unscoped-by-party route to the same POD/incident/expense data LegsController.GetDebrief already correctly restricts), ExceptionsController.List/Get (every exception in the company, including ones tied to other parties' loads/legs/invoices — §16.1's own scoped-portal-views were never built, so this stays internal-staff-only for now), CompaniesController.List/Get (the tenant's own BankingDetails/VatNumber/RegistrationNo), ApiClientsController.List/Get (system-to-system ClientId values), FunctionsController.List and RolesController.List/Get (the internal function catalog and which roles hold which functions), and FinancialPeriodsController.DebtorsAging (every Client's aged-debt buckets in one call, no per-client filter — a Customer Portal contact's own AR view is ClientsController.CreditStatus instead). None of these are part of either portal's documented scope, so each now Forbids any portal caller outright, the same pattern already established for the Load mutation actions. Verified live: all seven return a clean 403 for both portal types where reachable, and remain fully accessible to internal staff.
A third, adversarial audit pass — this time deliberately re-checking the two fixes above rather than trusting their own claims, plus a from-scratch matrix over all 26 controllers — found the second round's own justification for skipping DebriefsController was itself wrong: LegsController.GetDebrief gated its portal check behind if (SubcontractorId is not null), so a Customer Portal contact (SubcontractorId null) fell straight through to an unconditional return — the identical bug shape as the critical fix above, a fourth copy that slipped through both prior rounds on this same controller. Also found: UsersController.List/Get (every internal user and every other party's portal contacts, tenant-wide — email, display name, company-role assignments), FinancialPeriodsController.List/Get and FinancialYearsController.List/Get (the financial calendar structure, inconsistent with DebtorsAging's own fix in the same file), and six master-data controllers neither prior round's file list actually included — Commodities/CostCentres/Drivers/ExpenseTypes/Locations/Vehicles — all with the same no-policy, no-portal-check gap (Drivers notably exposing LicenceCode/LicenceExpiry/PdpExpiry). One provisioning-hygiene gap beyond a portal contact's own reach: RolesController.GrantFunction validated a Role's functions only at the moment a portal contact was first assigned it (2463fac) — granting a non-portal function to that Role afterward had no re-check, silently upgrading every contact already holding it to a full internal-staff session on their next token refresh. All closed the same way as every prior fix in this section — an outright Forbid for any portal caller on actions outside either portal's documented scope, and GrantFunction now refuses a non-portal.* function if the target Role is already assigned to any portal contact. Verified live: every one of the newly-found gaps returns a clean 403 (or 400, for GrantFunction), with legitimate own-party access and every internal-staff action unchanged.

14Data Retention & Privacy Compliance

Every Tenant is the Data Controller for the personal data it puts into the system — its own drivers, its clients' and subcontractors' contacts, its own staff. The platform operator is the Data Processor, bound by a Data Processing Agreement per tenant. GDPR (for EU-linked clients) and POPIA (for South African operations) are treated as one shared set of obligations — the two regimes define near-identical data subject rights — implemented as configurable policy and enforced workflow, not a one-off audit checkbox.

14.1Controller/processor relationship & data residency

  • Hosting region is selectable per Tenant (e.g. an EU customer's data stays in an EU Azure region; a South African customer's in a local one), satisfying GDPR's cross-border transfer restrictions and POPIA's equivalent. The Tenant isolation already built for §4.1 is what makes region-pinning a deployment choice rather than a redesign.
  • Any cross-tenant access by the break-glass Platform Support role (§4.1) is itself a processing activity under the DPA, and is captured like everything else by the audit trail (§12).

14.4Breach handling

A confirmed personal-data breach is notified to the relevant regulator — the EU/UK supervisory authority under GDPR within 72 hours, or South Africa's Information Regulator under POPIA "as soon as reasonably possible" — and to affected data subjects where required. The audit trail (§12) is what makes scoping a breach (which tenant, which records, which time window) a query rather than a forensic exercise.

14.5Field-level encryption

Banking details — Company.BankingDetails and Subcontractor.BankingDetails — are encrypted at the field level using ASP.NET Core's Data Protection API, via an EF Core value converter that encrypts on write and decrypts on read transparently: no controller or service needs to know these columns are ciphertext at rest. The protector uses a versioned purpose string ("Tms.BankingDetails.v1") — Data Protection derives a cryptographically independent key per purpose from the same key ring, so a future second protected field, or a deliberate re-key to a "v2" purpose, can never cross-contaminate with this one. The key ring itself is persisted to the same database as the data it protects (a DataProtectionKeys table), rather than a per-machine filesystem folder that wouldn't survive a redeploy or a second app instance.

Not yet production-real: with no explicit key-protection configured, ASP.NET Core falls back to its platform default for encrypting the key ring itself — DPAPI on Windows, tied to the local machine/user. A real deployment needs an explicit .ProtectKeysWithAzureKeyVault(...) (or equivalent KMS integration) so the key ring is wrapped by a real, centrally-managed key rather than OS-level protection — the same "structurally correct now, real once it exists" gap as several other pieces of this design before their dependencies existed.
Implemented and verified: confirmed directly against the raw SQL Server column — a Subcontractor's banking details written as "FNB, Acc 62123456789, Branch 250655" is stored as an opaque, unrelated ciphertext blob, while the same value read back through the API decrypts to the original text exactly. A pre-existing plaintext row from before this feature existed (this Company's own demo banking details, and a Subcontractor created in earlier testing) was migrated in place by a one-time startup fix-up rather than left to crash on first read — confirmed idempotent on a second restart, with no further rows touched.
Known gap, not addressed here: §14.2 lists Driver personal data as including "Licence, ID number, contact details, medicals," but the current Driver entity captures none of an ID number, contact details, or medical information — only LicenceCode (the licence class, e.g. Code 14) and its expiry. Nothing here is stored in plain text that shouldn't be, since it isn't stored at all; but §14.2's own table currently overstates what's actually captured. Adding those fields is a separate piece of work, deliberately not bundled into this one — whatever encryption approach applies to them should be decided at the point they're actually added, not spent now on fields that don't exist.

15Backup & Disaster Recovery

Backups protect against data loss; disaster recovery protects against losing an entire region. Both have to respect the same tenant boundaries and data-residency rules already built for multi-tenancy (§4) and privacy (§14) — a restore or failover is never an excuse to move a tenant's data somewhere it isn't allowed to be, or to expose one tenant's data while recovering another's.

15.1Backup strategy & recovery point

  • Automated full, differential, and transaction-log backups (native to Azure SQL, or SQL Server backup on-prem) give point-in-time restore within the retention window — target RPO ≤ 15 minutes for transactional data (Load, Invoice, Debrief, and everything else in §05).
  • The audit trail (§12) is backed up on the exact same schedule as the data it documents — never treated as disposable log output, since its entire purpose is to survive whatever happened to the primary data.
  • Backups are encrypted at rest with the same key management as live data (§14.5). The backup retention window is itself short relative to the statutory retention periods in §14.2 — a backup is a short-term operational safety net, not a second system of record, so it ages out well before it could become a forgotten copy of data that was erased under §14.3.

  • For silo tenants (their own dedicated database, §4.2), restore is a native point-in-time restore of just that one database — simpler, and part of why a large or regulated customer might specifically choose the silo model.
  • Every restore, partial or full, is itself an audited event (§12): who authorised it, what was restored, and for which tenant.

15.3High availability vs. regional disaster recovery

  • High availability — zone-redundant failover within a region — handles infrastructure failure with near-zero downtime and is always on.
  • Disaster recovery — a geo-replicated secondary region — handles a full regional outage. A tenant's secondary region is chosen from the same residency-approved set as its primary (§14.1): an EU tenant's DR copy stays in the EU, a South African tenant's in an approved regional pair, so failing over never creates a fresh cross-border transfer problem in the middle of an incident.
  • Target RTO ≤ 4 hours for a full regional failover of the platform; a single-tenant restore (§15.2) is typically far faster since it doesn't require a region-wide failover at all.

15.4Testing & assurance

An untested backup is not a backup. Restore drills run on a fixed schedule (quarterly, at minimum) against a scratch environment, exercising the exact pooled-tenant extraction procedure in §15.2 — not just confirming a backup file exists. Findings from each drill feed back into the runbook and are tracked like any other operational risk.

17Non-Functional Requirements

Security

Encryption in transit (TLS) and at rest, field-level encryption for banking data (§14.5), OWASP-aligned API hardening, and SQL Server Row-Level Security enforcing tenant isolation as a second, independent layer beneath the application (§4.1).

Scalability

Stateless API tier behind a load balancer, read replicas for reporting queries, horizontal scale-out per traffic growth as countries are added.

Localisation

UI strings, date/number formats, and legal document templates configurable per country; currency and unit formatting follow the user's company locale.

Auditability

Treated as a first-class platform function, not a per-module afterthought — full detail in §12.

Availability

Target 99.9% for the API tier; scheduled maintenance windows communicated per region to avoid peak dispatch hours; full backup/DR posture and RPO/RTO targets in §15.

Observability

Structured logging, distributed tracing across API modules, and health/metrics endpoints for infrastructure monitoring.

Implemented: HSTS (production only — Program.cs skips it in Development so a local HTTP dev loop still works) and baseline response headers (X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: strict-origin-when-cross-origin) on every response. Worth revisiting only if a future consumer genuinely calls this API from a different origin than the one serving it.
